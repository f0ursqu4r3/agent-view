## 1. Codex daemon probe (`spikes/codex-daemon-probe.ts`)

### Decision: DAEMON_SOURCE=no-go

Reason: no loaded thread to verify side effects.

`thread/loaded/list` returned `{"data":[],"nextCursor":null}` in every successful run (4 runs, including one at the end of the task). With no loaded thread, check (a) cannot be verified. The rules do not allow `thread/resume` for a thread that is not loaded, so the probe never sent it. Re-run the probe with one loaded thread to change this decision.

### Finding that changes the plan: the control socket speaks WebSocket

The brief assumed newline-delimited JSON through `codex app-server proxy`. That is wrong.

- A raw JSON line sent to the proxy gets no reply (initialize timed out after 10 s, 0 bytes on stdout and stderr).
- An HTTP upgrade request sent through the proxy returns `HTTP/1.1 101 Switching Protocols`, with header `x-codex-websocket-max-unfragmented-message-bytes: 16777216`.
- So the proxy passes raw bytes. The client must do the WebSocket handshake and frame JSON-RPC messages as text frames (client frames masked, no extensions offered).
- The probe contains a 60-line WebSocket client (handshake, text frames, ping/pong, close). It works the same over the proxy's stdio and over a direct unix socket connection.
- The collector must carry this client, or use Bun's `WebSocket` over a unix socket if that path works. Bun's `WebSocket` over a unix socket was not tested.

### Evidence

- `initialize` result shape (strings shown as lengths): `{ userAgent: <str:89>, codexHome: <str:28>, platformFamily: <str:4>, platformOs: <str:5> }`.
- `thread/loaded/list` result shape: `{ data: [], nextCursor: null }`.
- Notifications received after `initialized` (counts per run): `configWarning` 1, `remoteControl/status/changed` 1, `account/updated` 1. No other notifications in the listen window (20 s, because no thread was loaded).
- Counts of `thread/started`, `turn/*`, `item/*`, `thread/settings/updated`: 0. No server requests (approval prompts) arrived.
- The probe sent only: `initialize`, `initialized`, `thread/loaded/list`. The code has a hard allow-list that also covers `thread/read`, `thread/resume {threadId}` and `thread/unsubscribe`. None of those three were sent. Nothing was unsubscribed, because nothing was resumed.
- Strings are never printed: all output goes through a shape function that replaces every string with its length.

### (a) Side effects: not verifiable (no loaded thread)
### (b) Visibility of an interactive `codex` terminal session in `thread/loaded/list` or `thread/started`: not tested
### (c) Latency

- `item/started` to receipt: not measured (no `item/started` events).
- The probe computes it as `Date.now() - params.startedAtMs`. The schema has `startedAtMs` on `item/started`.
- Transport overhead, measured with 300 round trips of `thread/loaded/list` per transport (one connection each):

| Transport | min | p50 | p95 | max |
|---|---|---|---|---|
| proxy (`codex app-server proxy`) | 0.066 ms | 0.135 ms | 0.323 ms | 0.98 ms |
| direct unix socket | 0.051 ms | 0.111 ms | 0.227 ms | 0.447 ms |

The proxy adds about 0.02 ms at p50 and about 0.1 ms at p95, far below the 100 ms limit. So DAEMON_TRANSPORT=proxy.

### Known coverage gap

Whether terminal `codex` sessions are visible through the daemon is unknown. Treat them as not covered until a probe run with a loaded terminal session shows otherwise.

## 2. File-watch probe (`spikes/fs-watch-probe.ts`)

Method: 1,000 files, 10 sub-directories x 100 files, written over 2,000 ms (writer paced at 2 ms per file). Recursive mode: one `fs.watch(root, {recursive: true})`. Per-dir mode: `fs.watch` on the root and on each sub-directory. 3 runs per class and mode. Watchers armed 300 ms before the first write. Latency is measured from just before `writeFileSync` to the first event for that file. Settle time 1,500 ms after the last write.

Result: every class, every mode, every run: 1000/1000 files seen, 0 missed (0%).

| Class | Path | Recursive: missed, p95 | Per-dir: missed, p95 |
|---|---|---|---|
| home | `<repo>/test/.tmp/…` (under $HOME) | 0 / 0 / 0, 53.8-55.4 ms | 0 / 0 / 0, 53.1-54.9 ms |
| tmpdir | `realpathSync(os.tmpdir())/…` (`/private/var/folders/…/T`) | 0 / 0 / 0, 54.3-55.4 ms | 0 / 0 / 0, 54.1-54.9 ms |
| private-tmp | `/private/tmp/…` | 0 / 0 / 0, 54.0-54.3 ms | 0 / 0 / 0, 54.5-54.9 ms |
| symlink | symlink in `test/.tmp` to a real dir under $HOME | 0 / 0 / 0, 53.7-54.7 ms | 0 / 0 / 0, 52.5-54.6 ms |

Event counts per 1,000 files: recursive 1003-1017, per-dir 1000-1012 (a few duplicate `change` events). No unknown events.

Extra variants (3 runs each, same method), all 0 missed in both modes:
- `/private/tmp` with sub-directories created after the watcher armed (recursive and per-dir).
- `/private/tmp` with a separate process doing the writes.
- `/tmp/...` (the symlinked spelling of `/private/tmp`).
- `$HOME` class with a separate process doing the writes.
- Watching the `/private/tmp` root itself, recursive, 200 files at depth 2 and depth 5, with and without arming delay: 100% of own events seen (scratch test, not kept).

### Conflict with the "known before the probe" note

The brief says that on this Mac, on 2026-11-17, Bun's recursive watch reported no events under `/private/tmp`. This task could not reproduce it with Bun 1.4.4: 0% missed, in every variant above. The decision rule in the brief ("per-dir if recursive misses more than 1%") gives `recursive` for all four classes. I could not find the cause of the earlier observation (suspects: a different Bun build, a sandboxed process, or a watcher on a path that did not exist yet). Recommendation for the collector: at watch start, write and delete a canary file in each watch root and fall back to per-dir if no event arrives within 1 s.

### Latency note

p95 is about 54 ms in every case. This looks like a fixed coalescing interval in the watcher, not a per-class cost. It fits the 1-second event-to-pixel budget.

Probe files lived under `test/.tmp/` (git-ignored), `/private/var/folders/.../T` and `/private/tmp`, and were removed after each run. `test/.tmp/` is empty after the runs.

## 3. PixiJS stress (`spikes/pixi-stress/`)

Scene: 3,000 file nodes (circle sprites, phyllotaxis layout) with BitmapText labels; 50 agent sprites (25 orange, 25 blue) with additive-blend glow; 200 effect lines per second (450 ms life, fade out). Canvas 2560x1440, resolution 1, antialias off, WebGL. The page shows a live FPS readout and sets `window.__fps` (mean of `app.ticker.FPS` over the last 10 s) and `window.__fpsFrames` (frame count over the last 10 s). Run it with `bun spikes/pixi-stress/serve.ts [port]`. Query variants: `glow=sprite|filter`, `labels=lazy|all`, `lines=sprite|graphics`, `zoom`, `w`, `h`, `nodes`, `agents`, `rate`. Automated measurement: `GPU=1 [UNCAP=1] bun spikes/pixi-stress/measure.ts "<query>" ...`.

### Renderer facts

- Default headless Chromium: WebGL renderer `ANGLE (Google, Vulkan 1.3.0 (SwiftShader Device ...))`. Software.
- Headless Chromium with `--use-angle=metal --use-gl=angle --enable-gpu --ignore-gpu-blocklist`: WebGL renderer `ANGLE (Apple, ANGLE Metal Renderer: Apple M4 Max, Unspecified Version)`. GPU-backed. `renderer.name` is `webgl` in both.

### Results at 2560x1440 (viewport 2560x1440, dpr 1)

The GPU runs are vsync-capped, so they show 60.0 and no headroom. The uncapped column (`--disable-gpu-vsync --disable-frame-rate-limit`) shows headroom; use `frames/s`, because the mean of `ticker.FPS` is skewed when frame times vary.

| Variant | GPU, vsync: `__fps` | GPU, uncapped: frames/s | Software (SwiftShader): `__fps` |
|---|---|---|---|
| default (sprite glow, lazy labels, sprite lines, zoom 1) | 60.0 | 755 | 39.7 |
| `labels=all` (3,000 labels alive) | 60.0 | 132 | 13.8 |
| `glow=filter` (BlurFilter on 50 agents) | 60.0 | 209 (one 104 ms frame at start) | 24.5 |
| `lines=graphics` (one Graphics redrawn per frame) | 60.0 | 494 | not run |
| `zoom=2` (lazy labels, viewport-culled) | 60.0 | 247 | not run |
| `zoom=2&labels=all` | 60.0 | 134 | not run |
| `rate=1000` (5x event rate) | not run | 170 | not run |

Default variant, other numbers: about 560-600 labels visible at 1x (200 touches/s x 3 s window); about 1,600 at zoom 2. Update-callback cost 0.03-0.16 ms per frame, so the JS update is not the limit; GPU fill and draw calls are. No page errors.

### Decisions

- PIXI_GLOW: pre-rendered 128x128 radial-gradient canvas texture, one `Sprite` per agent with `blendMode = 'add'` and a tint. The filter variant is 3.6x slower uncapped and fails to reach 60 fps on software.
- PIXI_CULLING: a label exists only when the node was touched in the last 3 s, or when zoom is above 1.5 and the node is inside the viewport. Remove labels the rule no longer wants and reuse them from a pool. Use `BitmapText`, not `Text`. Keeping all 3,000 labels alive costs about 5.7x frame rate (755 to 132 uncapped).
- Line effects: pooled tinted `Texture.WHITE` sprites are the fastest of the two forms tried (755 vs 494 uncapped, but both are fine).
- 60 fps question (50 agents, 3,000 nodes, 200 events/s, 2560x1440): met on this Mac's GPU in headless Chromium (60.0, vsync-capped, at least 130 fps uncapped in every variant). Software rendering reaches only 39.7 fps, as expected. Status: pending controller check in a real browser (the page works standalone at the URL printed by `serve.ts`).
