## 1. Codex daemon probe (`spikes/codex-daemon-probe.ts`)

### Decision: DAEMON_SOURCE=no-go

Reason (2026-11-18): `thread/resume {threadId}` caused no thread side effects, but `initialize` changes daemon-wide state. The first client after a daemon start sets the originator that the daemon writes into every thread it creates later. Every client sets the User-Agent suffix of all the daemon's model requests. The spec requires a side-effect-free rejoin, and the Global Constraints forbid writes to agent logs and threads. See "Runs on 2026-11-18" below.

First reason (2026-11-17): no loaded thread to verify side effects. `thread/loaded/list` returned `{"data":[],"nextCursor":null}` in every successful run (4 runs). The rules do not allow `thread/resume` for a thread that is not loaded, so the probe never sent it.

### Finding that changes the plan: the control socket speaks WebSocket

The brief assumed newline-delimited JSON through `codex app-server proxy`. That is wrong.

- A raw JSON line sent to the proxy gets no reply (initialize timed out after 10 s, 0 bytes on stdout and stderr).
- An HTTP upgrade request sent through the proxy returns `HTTP/1.1 101 Switching Protocols`, with header `x-codex-websocket-max-unfragmented-message-bytes: 16777216`.
- So the proxy passes raw bytes. The client must do the WebSocket handshake and frame JSON-RPC messages as text frames (client frames masked, no extensions offered).
- The probe contains a 60-line WebSocket client (handshake, text frames, ping/pong, close). It works the same over the proxy's stdio and over a direct unix socket connection.
- The collector must carry this client, or use Bun's `WebSocket` over a unix socket if that path works. Bun's `WebSocket` over a unix socket was not tested.

### Evidence (runs of 2026-11-17)

- `initialize` result shape (strings shown as lengths): `{ userAgent: <str:89>, codexHome: <str:28>, platformFamily: <str:4>, platformOs: <str:5> }`.
- `thread/loaded/list` result shape: `{ data: [], nextCursor: null }`.
- Notifications received after `initialized` (counts per run): `configWarning` 1, `remoteControl/status/changed` 1, `account/updated` 1. No other notifications in the listen window (20 s, because no thread was loaded).
- Counts of `thread/started`, `turn/*`, `item/*`, `thread/settings/updated`: 0. No server requests (approval prompts) arrived.
- The probe sent only: `initialize`, `initialized`, `thread/loaded/list`. The code has a hard allow-list that also covers `thread/read`, `thread/resume {threadId}` and `thread/unsubscribe`. None of those three were sent. Nothing was unsubscribed, because nothing was resumed.
- Strings are never printed: all output goes through a shape function that replaces every string with its length.

### (a) Side effects

**Thread level (`thread/resume {threadId}`): pass.**

- `turn/started` after the resume: 0 (runs 3 and 4). The turn in progress at the resume (run 3) went on and ended normally: the terminal printed all 90 ticks and the one-line answer.
- `thread/settings/updated`: 0. Server requests (approval prompts): 0.
- `thread/read` fingerprint (model, provider, reasoning effort, cwd, ephemeral, name, path, source, parent, fork): unchanged after the resume and after the 45 s window. Model and reasoning effort: unchanged.
- The resume result carries the approval policy and the sandbox. It agrees with `thread/read` on model, provider, reasoning effort and cwd. Its settings fingerprint, which includes approval policy and sandbox, was `ceec85940efa` in both run 3 and run 4, so the run-3 resume did not change them. Their lengths (5 and 14) fit the launch flags (`never`, `workspaceWrite`).
- On every resume the daemon sends snapshots, not changes: `thread/goal/cleared` (the binary calls it the "thread goal resume snapshot"; the thread had no goal), `thread/tokenUsage/updated`, and one `deprecationNotice` per connection (text not printed; probably the full-history resume).
- One idle thread in run 3 rejected the resume with JSON-RPC error `-32600` (message of 67 characters, not printed). Its settings did not change. It was no longer loaded in run 4.
- Not tested: a thread with an active goal (the daemon has "restore goal runtime after thread resume" logic), and a thread waiting on an approval.

**Connection level (`initialize`): fail.** Check (a) as written in the plan looks only at turns and settings, so it missed this. It was found in the test thread's own rollout.

- The daemon wrote the terminal test thread's rollout (`session_meta` at 17:30:38, `cli_version` 0.170.0) with `originator: "agent-view-probe"`, the probe's `clientInfo.name`. The terminal client attached after runs 1 and 2 had ended, and its own name was not used.
- Run 5 attached with `clientInfo.name` `agent-view-ua-check`. The `userAgent` in its `initialize` result did not start with that name, but it contained `(agent-view-ua-check; `.
- So: the originator is set once per daemon process, by the first client that sends `initialize`. The probe was the first client after the daemon's start at about 03:57 UTC. The User-Agent suffix `(<clientInfo.name>; <version>)` is daemon-wide and set by every `initialize`.
- Effects: every thread the daemon creates later records the attaching tool as its originator (rollout `session_meta.originator`, and the `originator` column of the daemon's `threads` table), and the daemon sends it upstream. All the daemon's model requests carry the last client's User-Agent suffix. Both last until the daemon restarts.
- Cleanup: with the owner's consent, the agent closed its test terminal session and ran `codex app-server daemon restart` at 17:36:49 UTC (new pid, status `running`). No client attached after the restart. The test thread's rollout keeps `originator: "agent-view-probe"`.

### (b) Visibility

- The Codex desktop app does not use the shared daemon. It runs its own `codex app-server` as a child process over stdio (`cli_version` 0.169.0-alpha.11.1). Its threads never appear in the daemon's `thread/loaded/list`: runs 1 and 2 saw 0 threads while a desktop thread was writing its log.
- Each VS Code window with the Codex extension also runs its own `codex app-server`.
- Interactive terminal `codex` (0.166.0; feature `daemon_auto_start` is on; `--no-daemon` turns it off) runs its thread in the shared daemon. It appears in `thread/loaded/list` (runs 3 and 4).
- `source` is `vscode` for terminal threads and for desktop threads, so it cannot tell them apart.
- `thread/started`: not observed. No thread started during a listen window.
- `~/.codex` is a symlink to `~/.codex-accounts/work`. Both accounts' `app-server-control.sock` paths point to one socket under `/private/tmp/codex-daemon-<uid>/`. The daemon's `codexHome` is `~/.codex`, which gives the log scope `work`.
- IDs match the log adapter: a `commandExecution` item id (41 characters, prefix `exec-`) is the same in the daemon's `itemId` and in the log's `item_completed`. Direct calls use `call_…` ids (37 characters). Deduplication by (`agentId`, `callId`) in `CollectorState` would work.

### (c) Latency

- `item/started`, receipt time minus `startedAtMs`: n = 3, 0–1 ms. `item/completed`, receipt time minus `completedAtMs`: n = 3, 1–3 ms. Both through the proxy, far below the 1 s budget.
- `item/commandExecution/outputDelta`: 45 in the 45 s window for a command that prints one line per second. Deltas have no timestamp.
- Proxy round trip for `thread/loaded/list` (40 samples per run): p50 0.17–0.32 ms, p95 0.33–0.85 ms. DAEMON_TRANSPORT stays `proxy`.
- Wire shapes seen (strings replaced): `item/commandExecution/outputDelta` `{threadId, turnId, itemId, delta}`; `item/started` `{item: {type, id, …, startedAtMs, completedAtMs}, threadId, turnId, startedAtMs}`; `item/completed` adds `completedAtMs` and `contentTokenCount`.

### Re-opening Task 9

Re-open it only when one of these is true:

1. Codex offers a passive attach whose `initialize` sets neither the originator nor the User-Agent suffix.
2. The owner accepts both effects in writing, and the spec's read-only rule is changed to allow them.

Attaching only after another client has attached would avoid the originator write, but not the User-Agent change. The collector also cannot tell whether another client attached first without attaching itself.

Even with a go, the daemon covers only terminal `codex` sessions on this machine. Desktop and VS Code threads stay log-only.

### Known coverage gap

Codex threads come from their session logs only: no start events and no live output for nested commands. This holds for all Codex clients, including the desktop app, whose threads the daemon cannot see.

### Before the next probe run

Do not run the probe again without the owner's consent. `initialize` alone changes daemon-wide state (see (a)). After any run, ask the owner whether to restart the daemon.

The probe refuses to run unless `AGENT_VIEW_PROBE_RESUME=1` is set: without it, it prints why and exits 0, and sends nothing. Preconditions m1, m2, m3, m4 and m6 were met on 2026-11-18 (see the header of `spikes/codex-daemon-probe.ts` and the offline check above):

- **m1.** Model and reasoning effort are printed only as "unchanged" booleans and hashes.
- **m2.** Each `turn/started` is kept with its time after the resume and whether the resume result listed the turn. A turn that the resume did not list, on a resumed thread, inside 10 s after the resume, counts as suspect.
- **m3.** The resume-result fingerprint includes the approval policy and the sandbox. It is compared with `thread/read` and with any `thread/settings/updated` payload.
- **m4.** `checkOutgoing()` checks that `thread/resume`, `thread/read` and `thread/unsubscribe` params equal exactly `{threadId}`, that the thread is in the first `thread/loaded/list`, and that no message lacks a method.
- **m6.** The default run is 45 s. The probe warns on stderr first and stops at the first server request.

## 2. File-watch probe (`spikes/fs-watch-probe.ts`)

Method: 1,000 files, 10 sub-directories x 100 files, written over 2,000 ms (writer paced at 2 ms per file). Recursive mode: one `fs.watch(root, {recursive: true})`. Per-dir mode: `fs.watch` on the root and on each sub-directory. 3 runs per class and mode. Watchers armed 300 ms before the first write. Latency is measured from just before `writeFileSync` to the first event for that file. Settle time 1,500 ms after the last write.

Result: every class, every mode, every run: 1000/1000 files seen, 0 missed (0%).

| Class | Path | Recursive: missed, p95 | Per-dir: missed, p95 |
|---|---|---|---|
| home | `<repo>/test/.tmp/…` (under $HOME) | 0 / 0 / 0, 53.8-55.4 ms | 0 / 0 / 0, 53.1-54.9 ms |
| tmpdir | `realpathSync(os.tmpdir())/…` (`/private/var/folders/…/T`) | 0 / 0 / 0, 54.3-55.4 ms | 0 / 0 / 0, 54.1-54.9 ms |
| private-tmp | `/private/tmp/…` | 0 / 0 / 0, 54.0-54.3 ms | 0 / 0 / 0, 54.5-54.9 ms |
| symlink | symlink in `test/.tmp` to a real dir under $HOME | 0 / 0 / 0, 53.7-54.7 ms | 0 / 0 / 0, 52.5-54.6 ms |

Event counts per 1,000 files: recursive 1003-1017, per-dir 1000-1012 (a few duplicate `change` events). No unknown events.

Extra variants (3 runs each, same method), all 0 missed in both modes:
- `/private/tmp` with sub-directories created after the watcher armed (recursive and per-dir).
- `/private/tmp` with a separate process doing the writes.
- `/tmp/...` (the symlinked spelling of `/private/tmp`).
- `$HOME` class with a separate process doing the writes.
- Root-watch variant (`private-tmp-ROOT-watch`, kept in the probe): the recursive watcher sits on `/private/tmp` itself, the shared busy root, and the 1,000 files are written in a sub-directory of it. 5 runs: 1000/1000 seen, 0 missed (0%) each run, events 1005-1017, p95 53.8-55.6 ms. A further run inside the full probe gave the same result. Recursive only; per-dir does not apply to a root watch.
- Earlier scratch test (not kept): `/private/tmp` root, recursive, 200 files at depth 2 and depth 5, with and without arming delay: 100% of own events seen.

### Conflict with the "known before the probe" note

The brief says that on this Mac, on 2026-11-17, Bun's recursive watch reported no events under `/private/tmp`. This task could not reproduce it with Bun 1.4.4: 0% missed, in every variant above. The decision rule in the brief ("per-dir if recursive misses more than 1%") gives `recursive` for all four classes. I could not find the cause of the earlier observation (suspects: a different Bun build, a sandboxed process, or a watcher on a path that did not exist yet). The collector keeps a per-dir fallback mode (ruling R8). A canary-file self-test is not allowed: it would write into watched projects.

### Latency note

p95 is about 54 ms in every case. This looks like a fixed coalescing interval in the watcher, not a per-class cost. It fits the 1-second event-to-pixel budget.

Probe files lived under `test/.tmp/` (git-ignored), `/private/var/folders/.../T` and `/private/tmp`, and were removed after each run. `test/.tmp/` is empty after the runs.

## 3. PixiJS stress (`spikes/pixi-stress/`)

> The PixiJS probe code was removed in P2c (2026-11-19); the numbers below stay as measured.

Scene: 3,000 file nodes (circle sprites, phyllotaxis layout) with BitmapText labels; 50 agent sprites (25 orange, 25 blue) with additive-blend glow; 200 effect lines per second (450 ms life, fade out). Canvas 2560x1440, resolution 1, antialias off, WebGL. The page shows a live FPS readout and sets `window.__fps` (mean of `app.ticker.FPS` over the last 10 s) and `window.__fpsFrames` (frame count over the last 10 s). Run it with `bun spikes/pixi-stress/serve.ts [port]`. Query variants: `glow=sprite|filter`, `labels=lazy|all`, `lines=sprite|graphics`, `zoom`, `w`, `h`, `nodes`, `agents`, `rate`. Automated measurement: `GPU=1 [UNCAP=1] bun spikes/pixi-stress/measure.ts "<query>" ...`.

### Renderer facts

- Default headless Chromium: WebGL renderer `ANGLE (Google, Vulkan 1.3.0 (SwiftShader Device ...))`. Software.
- Headless Chromium with `--use-angle=metal --use-gl=angle --enable-gpu --ignore-gpu-blocklist`: WebGL renderer `ANGLE (Apple, ANGLE Metal Renderer: Apple M4 Max, Unspecified Version)`. GPU-backed. `renderer.name` is `webgl` in both.

### Results at 2560x1440 (viewport 2560x1440, dpr 1)

The GPU runs are vsync-capped, so they show 60.0 and no headroom. The uncapped column (`--disable-gpu-vsync --disable-frame-rate-limit`) shows headroom; use `frames/s`, because the mean of `ticker.FPS` is skewed when frame times vary.

|---|---|---|---|
| default (sprite glow, lazy labels, sprite lines, zoom 1) | 60.0 | 755 | 39.7 |
| `labels=all` (3,000 labels alive) | 60.0 | 132 | 13.8 |
| `glow=filter` (BlurFilter on 50 agents) | 60.0 | 209 (one 104 ms frame at start) | 24.5 |
| `lines=graphics` (one Graphics redrawn per frame) | 60.0 | 494 | not run |

Default variant, other numbers: about 560-600 labels visible at 1x (200 touches/s x 3 s window); about 1,600 at zoom 2. Update-callback cost 0.03-0.16 ms per frame, so the JS update is not the limit; GPU fill and draw calls are. No page errors.

### Decisions

- PIXI_GLOW: pre-rendered 128x128 radial-gradient canvas texture, one `Sprite` per agent with `blendMode = 'add'` and a tint. The filter variant is 3.6x slower uncapped and fails to reach 60 fps on software.
- PIXI_CULLING: a label exists only when the node was touched in the last 3 s, or when zoom is above 1.5 and the node is inside the viewport. Remove labels the rule no longer wants and reuse them from a pool. Use `BitmapText`, not `Text`. Keeping all 3,000 labels alive costs about 5.7x frame rate (755 to 132 uncapped).
- Line effects: pooled tinted `Texture.WHITE` sprites are the fastest of the two forms tried (755 vs 494 uncapped, but both are fine).
- 60 fps question (50 agents, 3,000 nodes, 200 events/s, 2560x1440): met on this Mac's GPU in headless Chromium (60.0, vsync-capped, at least 130 fps uncapped in every variant). Software rendering reaches only 39.7 fps, as expected. Status: pending controller check in a real browser (the page works standalone at the URL printed by `serve.ts`).
